What this comparison is measuring, and what it is not:

  etcd runs in a Linux container on a macOS host, so its writes cross a
  virtual machine boundary that Keel's do not. A ratio measured across
  that boundary is partly a measurement of the boundary. This harness
  exists so that the same comparison on Linux hardware is one command;
  the number below is not that comparison.

  The mechanism behind any difference is not a mystery: etcd stores in
  bbolt, a B+tree with a per-transaction fsync, and speaks gRPC over
  HTTP/2. Keel stores in an LSM with group commit, where one fsync
  retires every batch queued behind it, and speaks length-prefixed
  frames over TCP. Different trades, not different amounts of effort.

--- the asymmetry that dominates this comparison

etcd here is fsyncing inside a Linux virtual machine on a macOS host.
Keel is fsyncing natively with F_FULLFSYNC, which is the only primitive
on this platform that actually forces a drive cache flush — fdatasync on
Linux, and every fsync inside a Docker Desktop VM, may return once the
write reaches the host's page cache.

So the two sides are not making the same promise, and the gap below is
mostly that. A durability number compared against a number that may not
be durable is not a comparison of two systems; it is a comparison of two
definitions. The same script on Linux hardware, where both sides use the
same primitive against the same device, is the run that would settle it.

The honest internal control is Keel's own fsync-off arm:
results/bench/ablation-fsync-off.txt, where the same cluster with writes
neither ordered nor durable does four times the throughput at a quarter
of the latency. That is the cost of the promise, measured on one machine
with one variable changed.
